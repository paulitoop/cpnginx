# Переносная демонстрация ГОСТ mTLS

Стенд состоит из чистых Ubuntu-шлюзов, готового сервера партнёра и Vault. На шлюзах есть SSH и зависимости Ansible. КриптоПро CSP и Nginx устанавливает роль `cpnginx_install` из WSL. [Результаты проверок](VALIDATION.md)

## Подготовка

В Docker Desktop включите Linux containers и интеграцию с Ubuntu/WSL. В Ubuntu нужны `python3-venv`, `git`, `openssh-client` и `openssl`.

```bash
./lab/lab.sh prepare --nodes 1  # либо --nodes 2
./lab/lab.sh status
./lab/lab.sh check --stage before
```

`prepare` собирает отдельные образы шлюза и партнёра, скачивает Vault и Python-зависимости, получает роли с GitHub и запускает контейнеры. При повторной подготовке команда пересоздаёт шлюзы в чистом состоянии. Чтобы запустить уже существующие контейнеры, используйте `up --nodes 1`.

По умолчанию `prepare` берёт архив из соседней роли `ansible-role-cpnginx_install/files/linux-amd64_deb.tgz`. В текущей рабочей копии архив уже лежит на месте. При другой раскладке папок можно передать `--archive /absolute/path/linux-amd64_deb.tgz`. При повторном запуске доступна локальная копия из предыдущей подготовки. Архив исключён из Git.

Лицензия сервера хранится в Vault KV v2 по пути `cpnginx/licenses/partner`, поле `license`. Партнёр читает её при запуске через отдельный AppRole. На этой машине действующая лицензия уже перенесена. При первом запуске на новом стенде передайте `prepare --license-file /private/path/tls-server.license`. Утилита проверяет ключ перед записью в Vault. Шлюзы выступают клиентами TLS и используют демо-лицензию CSP.

По умолчанию файлы подготовки находятся в `~/.local/state/cpnginx-lab` в WSL. `LAB_STATE_DIR` меняет путь. `prepare --local-roles` использует соседние рабочие копии ролей для разработки. При первой подготовке скрипт выпускает тестовый УЦ, список отзыва и два PFX. `prepare --renew-certs` выпускает их заново. После перевыпуска обновите корень в Windows, клиентский секрет в Vault и серийный номер в YAML.

### Браузер Windows

Для прямого обращения нужен браузер с поддержкой ГОСТ TLS и установленный
КриптоПро CSP. Обычный curl или браузер без ГОСТ не подтверждает отказ
именно из-за отсутствия клиентского сертификата.

1. Добавьте в Windows hosts строку `127.0.0.1 cpnginx.example.test`.
2. Импортируйте **публичный** `assets/root.cer` из каталога состояния в
   доверенные корневые сертификаты тестового пользователя браузера.
3. Не импортируйте клиентский PFX в браузер: прямое обращение должно
   выполняться без клиентского ключа. При старых импортированных тестовых
   идентичностях используйте отдельного пользователя/профиль.

Скрипт не меняет Windows hosts и системное доверие. Созданный УЦ используется
только в лаборатории. После демонстрации удалите добавленное доверие и hosts.

## Показ

1. Запустите `prepare --nodes 1` и `status`. Покажите Ubuntu-шлюз, партнёра и Vault. Команда `check --stage before` проверяет, что КриптоПро Nginx на шлюзе ещё отсутствует. Перед повторным показом `reset-demo` возвращает это состояние и удаляет клиентский секрет из Vault.
2. Проверьте прямой доступ к партнёру. На этапе сравнения в Edge должен использоваться обычный TLS без ГОСТ, а в Яндекс Браузере должна работать поддержка ГОСТ и доверие тестовому УЦ.

   | Адрес | Edge без ГОСТ | Яндекс Браузер с ГОСТ |
   |---|---|---|
   | `https://cpnginx.example.test:15100/tls` | TLS не устанавливается | Открывается контрольная страница ГОСТ TLS |
   | `https://cpnginx.example.test:15101/mtls` | TLS не устанавливается | Сервер отклоняет запрос без клиентского сертификата |

3. Запустите `./lab/lab.sh install`. Плейбук выполняет роль установки. После `./lab/lab.sh check --stage installed` откройте `http://localhost:18080/`. Там появится **Welcome to nginx!**. [Плейбук установки](playbooks/install.yml)
4. Откройте `http://localhost:18200/ui/` и войдите по токену из `./lab/lab.sh token`. В KV v2 `cpnginx` создайте `demo/client`. В режиме JSON вставьте содержимое `~/.local/state/cpnginx-lab/vault-payload.json` с полями `pfx` и `pin`. В списке секретов можно показать `licenses/partner`, не открывая значение лицензии.
5. Создайте в GitHub файл `integrations/demo/demo-mtls.yaml` в ветке `main`. Возьмите содержимое из `~/.local/state/cpnginx-lab/demo-mtls.yaml` и сохраните commit. Для репетиции можно передать локальный каталог через `configure --configs-dir /absolute/path`.
6. Запустите `./lab/lab.sh configure`, затем `./lab/lab.sh check --stage after`. Обновите **тот же адрес** `http://localhost:18080/` в Edge. Теперь шлюз показывает защищённую страницу партнёра **«Доступ через ГОСТ mTLS»**. У второго шлюза адрес `http://localhost:18081/`.

Браузер обращается к шлюзу по HTTP. Шлюз устанавливает ГОСТ mTLS с партнёром, проверяет серверный сертификат и передаёт ответ обратно по тому же адресу. Прямой запрос из Яндекс Браузера по-прежнему отклоняется на странице mTLS без клиентского ключа.

При потере сети `configure --cached` использует последний скачанный commit GitHub. Для показа с этой опцией заранее скачайте нужную версию конфигурации.

## Формат интеграции

```yaml
name: demo-mtls
target_host: cpnginx.example.test
target_port: 5101
listen_port: 30443
cert_client: cpnginx/data/demo/client
cert_client_serial: "0xACTUAL_HEXADECIMAL_SERIAL"
comment: "Portable GOST mTLS demo"
```

Серийный номер берите из сгенерированного YAML. Для TLS без клиентского
сертификата оба поля `cert_client` и `cert_client_serial` опускаются.
Балансировщики, `layers` и `allowed_sources` исключены. Хосты шлюзов задаются
только в Ansible inventory, генерируемом для выбранного числа контейнеров.
Все интеграции выбранного каталога устанавливаются на все выбранные шлюзы.
Примеры в `integrations/examples` автоматически не применяются.
Пустой `integrations/demo` удаляет управляемые portal-конфигурации.

## Управление и ограничения

```bash
./lab/lab.sh status
./lab/lab.sh up --nodes 2
./lab/lab.sh up --nodes 1
./lab/lab.sh down
```

`down` сохраняет Vault volume и файлы подготовки. `reset-demo` удаляет только
лабораторный secret `demo/client` и пересоздаёт шлюзы. Остальные контейнеры и
Vault других проектов не затрагиваются. Удаление YAML в GitHub не выполняется.
После сброса для повторной установки снова загрузите PFX в Vault.

Порты публикуются только на `127.0.0.1`: SSH 2221/2222, прокси 18080/18081,
контроль TLS 15100, mTLS 15101, Vault 18200. Лимиты памяти: по 512 MiB на
Ubuntu-контейнер и 256 MiB на Vault, суммарно 1.25 GiB с одним шлюзом или
1.75 GiB с двумя, дополнительно расходуются ресурсы Docker Desktop и WSL.

Vault HTTP, root token для UI и автоматическая распечатка локального токена
по отдельной команде предназначены для изолированного показа. Приложение
читает PFX через отдельный AppRole с правом чтения `cpnginx/data/demo/*`.
Партнёр получает только `cpnginx/data/licenses/partner` через свой AppRole.
Пользователь с доступом к Docker/состоянию WSL имеет доступ к секретам стенда.
Очистка `always` покрывает обычную ошибку задачи, но не аварийное отключение
хоста или принудительное завершение всего Ansible-процесса.
Подготовка генератора CSP в контейнере является лабораторным механизмом и
не представляет собой сертифицированную процедуру получения энтропии.
Результаты измерений Docker следует фиксировать отдельно от старых VM-замеров.

Формат внешней гаммы (32 байта данных + 4 байта контрольной суммы) описан
в [руководстве КриптоПро по АРМ выработки внешней гаммы](https://cryptopro.ru/sites/default/files/docs/csp/50r3/%D0%96%D0%A2%D0%AF%D0%98.00101-03%2094%2001.%20%D0%90%D0%A0%D0%9C%20%D0%B2%D1%8B%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B8%20%D0%B2%D0%BD%D0%B5%D1%88%D0%BD%D0%B5%D0%B9%20%D0%B3%D0%B0%D0%BC%D0%BC%D1%8B.pdf).
Lab создаёт свежие порции из CSPRNG ОС при каждом старте; контрольная сумма
CRC32 проверена по выходу `genkpim` установленной версии CSP. Не переносите
этот способ в промышленное или сертифицированное развёртывание.
