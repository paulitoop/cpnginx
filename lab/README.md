# Переносная демонстрация ГОСТ mTLS

Фактически выполненные проверки и незавершённые шаги: [VALIDATION.md](VALIDATION.md).

Управление выполняется из Ubuntu/WSL. Docker Desktop запускает один или два
Ubuntu-шлюза, сервер партнёра и отдельный Vault. Ansible работает в WSL.
VirtualBox и прежний `/opt/work/ansible` этот стенд не изменяет.

## Подготовка заранее

Нужны Docker Desktop с Linux containers и интеграцией WSL, Git, Python 3 с
venv, OpenSSH client и OpenSSL. В Ubuntu:

```bash
sudo apt-get update
sudo apt-get install -y python3-venv git openssh-client openssl
cd /path/to/cpnginx
./lab/lab.sh prepare --archive /absolute/path/linux-amd64_deb.tgz --license-file /private/path/tls-server.license
./lab/lab.sh up --nodes 1
./lab/lab.sh check --stage before
```

`prepare` скачивает образы, Python-пакеты и обе роли с GitHub, собирает
локальный Ubuntu 24.04 с предоставленным дистрибутивом КриптоПро и создаёт
свежий тестовый УЦ, CRL и клиентский/серверный PFX. Старые сертификаты
исходного стенда истекли 03.07.2026 и здесь не используются.
Дистрибутив и образ с КриптоПро не публикуются.
Для серверной стороны используйте собственную подходящую лицензию TLS Server.
Обычная Demo CSP 5.0.13000 не обеспечила серверный handshake в проверенном
образе (`AcquireCredentialsHandle 0x80090307`). Нужен выданный вам ключ с
необходимыми правами; повторную установку и условия использования проверьте
по своей лицензии. `--license-file` копирует текстовый файл в приватное
состояние и передаёт его только контейнеру партнёра, не в образ и не в Git.
Без него можно подготовить стенд; `up` запросит заполненный файл лицензии.
Если CSP сообщает `License expired or not yet valid`, замените файл на
действующую лицензию. Для текущей уже подготовленной установки:

```bash
./lab/lab.sh prepare --license-file /private/path/current-tls-server.license
./lab/lab.sh up --nodes 1
./lab/lab.sh check --stage before
```

Значение ключа не печатается. Не вставляйте его в YAML интеграции или GitHub.

По умолчанию приватное состояние находится в Linux-файловой системе
`~/.local/state/cpnginx-lab` с закрытыми правами. `LAB_STATE_DIR` меняет путь.
Не размещайте это состояние в Git, OneDrive или общей папке.
`prepare --local-roles` нужен разработчику для проверки соседних рабочих копий.
`prepare --renew-certs` перевыпускает тестовую цепочку; после этого нужно
заново импортировать корень в браузер и загрузить новый клиентский секрет.
Повторная подготовка требует сети. Подготовленный `up` образы не скачивает.

### Браузер Windows

Для прямого обращения нужен браузер с поддержкой ГОСТ TLS и установленный
КриптоПро CSP. Обычный curl или браузер без ГОСТ не подтверждает отказ
именно из-за отсутствия клиентского сертификата.

1. Добавьте в Windows hosts строку `127.0.0.1 cpnginx.example.test`.
2. Импортируйте **публичный** `assets/root.cer` из каталога состояния в
   доверенные корневые сертификаты тестового пользователя браузера.
3. Не импортируйте клиентский PFX в браузер: прямое обращение должно
   выполняться без клиентского ключа. При старых импортированных тестовых
   идентичностях используйте отдельного пользователя/профиль.

Скрипт не меняет Windows hosts и системное доверие. Созданный УЦ используется
только в лаборатории. После демонстрации удалите добавленное доверие и hosts.

## Показ

```bash
./lab/lab.sh up --nodes 1    # либо --nodes 2
./lab/lab.sh reset-demo     # перед повторным показом
./lab/lab.sh check --stage before
```

1. Откройте `https://cpnginx.example.test:15100/tls`: контроль ГОСТ TLS.
2. Откройте `https://cpnginx.example.test:15101/mtls`: без клиентского ключа
   защищённая страница недоступна.
3. Откройте Vault `http://localhost:18200`. Локальный демонстрационный root
   token выводится отдельной командой `./lab/lab.sh token`.
4. В KV v2 `cpnginx` создайте secret `demo/client`. В режиме JSON вставьте
   содержимое `~/.local/state/cpnginx-lab/vault-payload.json`: поля `pfx` и
   `pin`. `pfx` содержит base64 ZIP с одним PFX, не base64 самого PFX.
5. В GitHub `paulitoop/cpnginx`, ветка `main`, создайте
   `integrations/demo/demo-mtls.yaml`. Содержимое возьмите из
   `~/.local/state/cpnginx-lab/demo-mtls.yaml` и сохраните commit.
6. Выполните `./lab/lab.sh configure`. Команда скачает актуальный commit и
   выведет его SHA; роль настроит выбранные шлюзы по SSH.
7. Выполните `./lab/lab.sh check --stage after` и откройте
   `http://localhost:18080/mtls`. Для второго шлюза: порт `18081`.

Участок браузер → локальный шлюз в этой упрощённой демонстрации использует
HTTP, шлюз → партнёр использует ГОСТ mTLS с проверкой сертификата и локальной
CRL. Это не полная схема защиты внутренней сети предприятия.
Клиентский ключ доступен пользователю сервиса шлюза, но не пользователю,
от имени которого выполняется прямая отрицательная проверка.

Если интернет на показе пропал, `configure --cached` явно использует
последний ранее скачанный commit. Изменения GitHub без сети не попадут в него.
`configure --configs-dir /absolute/path` является отдельным явным локальным
режимом; для обычной демонстрации он не нужен.

## Формат интеграции

```yaml
name: demo-mtls
target_host: cpnginx.example.test
target_port: 5101
listen_port: 30443
cert_client: cpnginx/data/demo/client
cert_client_serial: "0xACTUAL_HEXADECIMAL_SERIAL"
comment: "Portable GOST mTLS demo"
```

Серийный номер берите из сгенерированного YAML. Для TLS без клиентского
сертификата оба поля `cert_client` и `cert_client_serial` опускаются.
Балансировщики, `layers` и `allowed_sources` исключены. Хосты шлюзов задаются
только в Ansible inventory, генерируемом для выбранного числа контейнеров.
Все интеграции выбранного каталога устанавливаются на все выбранные шлюзы.
Примеры в `integrations/examples` автоматически не применяются.
Пустой `integrations/demo` удаляет управляемые portal-конфигурации.

## Управление и ограничения

```bash
./lab/lab.sh status
./lab/lab.sh up --nodes 2
./lab/lab.sh up --nodes 1
./lab/lab.sh down
```

`down` сохраняет Vault volume и файлы подготовки. `reset-demo` удаляет только
лабораторный secret `demo/client` и пересоздаёт шлюзы. Остальные контейнеры и
Vault других проектов не затрагиваются. Удаление YAML в GitHub не выполняется.
После сброса для повторной установки снова загрузите PFX в Vault.

Порты публикуются только на `127.0.0.1`: SSH 2221/2222, прокси 18080/18081,
контроль TLS 15100, mTLS 15101, Vault 18200. Лимиты памяти: по 512 MiB на
Ubuntu-контейнер и 256 MiB на Vault, суммарно 1.25 GiB с одним шлюзом или
1.75 GiB с двумя, дополнительно расходуются ресурсы Docker Desktop и WSL.

Vault HTTP, root token для UI и автоматическая распечатка локального токена
по отдельной команде предназначены для изолированного показа. Приложение
читает PFX через отдельный AppRole с правом чтения `cpnginx/data/demo/*`.
Пользователь с доступом к Docker/состоянию WSL имеет доступ к секретам стенда.
Очистка `always` покрывает обычную ошибку задачи, но не аварийное отключение
хоста или принудительное завершение всего Ansible-процесса.
Подготовка генератора CSP в контейнере является лабораторным механизмом и
не представляет собой сертифицированную процедуру получения энтропии.
Результаты измерений Docker следует фиксировать отдельно от старых VM-замеров.

Формат внешней гаммы (32 байта данных + 4 байта контрольной суммы) описан
в [руководстве КриптоПро по АРМ выработки внешней гаммы](https://cryptopro.ru/sites/default/files/docs/csp/50r3/%D0%96%D0%A2%D0%AF%D0%98.00101-03%2094%2001.%20%D0%90%D0%A0%D0%9C%20%D0%B2%D1%8B%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B8%20%D0%B2%D0%BD%D0%B5%D1%88%D0%BD%D0%B5%D0%B9%20%D0%B3%D0%B0%D0%BC%D0%BC%D1%8B.pdf).
Lab создаёт свежие порции из CSPRNG ОС при каждом старте; контрольная сумма
CRC32 проверена по выходу `genkpim` установленной версии CSP. Не переносите
этот способ в промышленное или сертифицированное развёртывание.
